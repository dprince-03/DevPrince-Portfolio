## `infra/` — containers and reverse proxy

```
infra/
├── docker/
│   ├── docker-compose.yml            Base: Postgres only (shared by dev and prod)
│   ├── docker-compose.override.yml   Dev overlay (auto-merged): server/client run from source, hot reload
│   ├── docker-compose.prod.yml       Prod overlay (explicit -f only): built images + nginx, no bind mounts
│   ├── Dockerfile.server             Multi-stage Express image, non-root user
│   ├── Dockerfile.client             Multi-stage Next.js standalone image, non-root user
│   ├── backup.sh                     Manual/cron Postgres backup — pg_dump + gzip, prints the restore command
│   ├── .dockerignore
│   └── .env.example                  Postgres creds + PUBLIC_ORIGIN for the prod stack
└── nginx/
    ├── nginx.conf                    Main config: gzip, security headers, websocket upgrade map
    ├── proxy_params.conf             Shared proxy headers, included explicitly per-location
    └── conf.d/default.conf           Reverse proxy: /api/* → server, everything else → client; rate-limited /api/auth/*; commented HTTPS template
```

## How the pieces talk to each other

- **Browser → client**: Next.js pages/components, using `NEXT_PUBLIC_API_URL` (dev: `http://localhost:5000`; prod: `""`, i.e. same-origin through nginx).
- **Client server-side code → server**: `API_INTERNAL_URL` (dev: `http://localhost:5000` on host / `http://server:5000` inside Docker; prod: `http://server:5000` on the compose network) — used by `app/admin/dashboard/layout.js` to verify the session cookie server-side before rendering.
- **Client/server → Postgres**: `DATABASE_URL`, always via the `postgres` service on the compose network.
- **Everything, in prod, through nginx**: a single public origin, `/api/*` routed to `server`, everything else to `client` — this is why the browser-facing `NEXT_PUBLIC_API_URL` can be empty in prod (no cross-origin requests, no CORS needed between client and server there).

## Running it locally

**Primary workflow: everything in Docker** (Postgres + server + client, one command). A native (no-Docker) path also still works for fast iteration if you ever want it — see below.

### Docker Compose — dev (recommended)

```bash
# From the repo root — explicitly passes both the base file and the dev overlay
docker compose -f infra/docker/docker-compose.yml -f infra/docker/docker-compose.override.yml up -d

# Watch logs (Ctrl-C just detaches, doesn't stop anything)
docker compose -f infra/docker/docker-compose.yml -f infra/docker/docker-compose.override.yml logs -f
```

This builds nothing custom — it runs `node:20-alpine` containers that `npm install` and `npm run dev` against your bind-mounted `client/` and `server/` source, so edits on your machine still hot-reload inside the containers. First boot is slower (installing deps inside the containers); subsequent boots reuse the `server_node_modules`/`client_node_modules` named volumes.

Ports: server `5000`, Postgres `5434`. **Client is mapped to host `3002`, not the Next.js default `3000`** — on this machine ports 3000 and 3001 are both already held by unrelated processes, so `docker-compose.override.yml` remaps `3002:3000` (container-internal port is still 3000; only the host side changed). If that conflict doesn't exist on your machine, feel free to change it back to `3000:3000`.

Tip: run `cd infra/docker && docker compose up -d` instead and Compose will pick up `docker-compose.yml` + `docker-compose.override.yml` automatically, without needing both `-f` flags.

**Recurring gotcha: stale Turbopack cache inside the client container.** A handful of times now, an edit to a `client/` file has been correctly saved to disk but the running dev server keeps serving the *previous* version — sometimes a fully stale page, sometimes a half-applied edit (e.g. one usage of a renamed variable updated, another still referencing the old name, throwing a `ReferenceError` for a variable that clearly exists in the file on disk). This isn't a real code bug each time; it's Turbopack's persistent cache under `client/.next/` getting out of sync with the bind-mounted source, which seems more prone to happen across Docker's virtiofs-backed bind mount than with a native filesystem. If a change doesn't show up (or an error references code that isn't actually there anymore), don't waste time re-diagnosing — clear it and restart:

```bash
docker compose -f infra/docker/docker-compose.yml -f infra/docker/docker-compose.override.yml exec client sh -c "rm -rf .next"
docker compose -f infra/docker/docker-compose.yml -f infra/docker/docker-compose.override.yml restart client
```

You still need `server/.env` to exist before the server container will boot (it reads `ADMIN_EMAIL`/`ADMIN_PASSWORD`/`JWT_SECRET` from it), and to seed the database once:

```bash
[ -f server/.env ] || cp server/.env.example server/.env   # then edit: ADMIN_EMAIL, ADMIN_PASSWORD, a real JWT_SECRET

# Seed runs inside the already-running server container — no local npm install needed
docker compose -f infra/docker/docker-compose.yml -f infra/docker/docker-compose.override.yml exec server npm run seed
```

Then visit `http://localhost:3002` for the public site and `http://localhost:3002/admin/login` for the dashboard.

**Docker Desktop resource note**: if containers start and then all exit together within a few seconds (exit code `137` = OOM-killed, or `143` = SIGTERM from a VM restart), that's Docker Desktop's own VM running low on disk or memory — it has its own allocation, separate from the host's. Check via `docker run --rm node:20-alpine sh -c "df -h /; free -h"`; fix via Docker Desktop → Settings → Resources (bump Memory/Disk), or reclaim space with `docker builder prune -af` and removing unused images (`docker image prune -a` — review first, this affects other projects' cached images too). Starting services one at a time (`... up -d postgres server`, wait, then `... up -d client`) avoids a startup memory spike from both `npm install`s running at once.

### Native (no Docker for the app, just Postgres) — optional, for fast iteration

```bash
# 1. Start Postgres only, via Docker (host port 5434 — 5432 is often already taken)
docker compose -f infra/docker/docker-compose.yml up -d postgres

# 2. Backend: install, migrate, seed, run
cd server
[ -f .env ] || cp .env.example .env   # then edit .env: set ADMIN_EMAIL, ADMIN_PASSWORD, generate JWT_SECRET
npm install
npx prisma migrate dev      # first run only (or after schema changes)
npm run seed                # creates the admin user, prints the TOTP secret — add it to an authenticator app
npm run dev                 # http://localhost:5000

# 3. Frontend (separate terminal): install, run
cd client
[ -f .env.local ] || cp .env.local.example .env.local   # same caveat as above
npm install
npm run dev                 # http://localhost:3000 (or the next free port if 3000 is busy)
```

To regenerate a JWT secret: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`.

### Production-shaped stack (built images + nginx)

```bash
cp infra/docker/.env.example infra/docker/.env   # fill in a real POSTGRES_PASSWORD — required, no insecure default
docker compose -f infra/docker/docker-compose.yml -f infra/docker/docker-compose.prod.yml up -d --build
```

Serves everything through nginx on `http://localhost` (port 80) — no ports for `client`/`server` are published directly. Useful for testing the prod build path (standalone Next.js output, `prisma migrate deploy` on boot, nginx routing) before an actual domain/TLS cert exist. See `infra/nginx/conf.d/default.conf` for the commented-out HTTPS block to enable once a real domain is in place.

### Stopping / cleaning up

```bash
docker compose -f infra/docker/docker-compose.yml -f infra/docker/docker-compose.override.yml down   # stop dev stack
docker compose -f infra/docker/docker-compose.yml down                                                # stop Postgres only
# add -v to also delete the pgdata volume (wipes the database) — only if you actually want that
```
